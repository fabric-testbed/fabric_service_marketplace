# FABRIC Service Portal

Lets FABRIC researchers publish services, and lets other FABRIC users find and
use them. A service either runs on the author's slice nodes (reached over
FABnetv6 through the gateway) or is an existing website the portal links to.

```bash
git clone https://github.com/fabric-testbed/fabric_service_marketplace.git
```

**To deploy, follow [docs/SETUP.md](docs/SETUP.md).** Design: [docs/DESIGN.md](docs/DESIGN.md).

## What runs where

```
 Browser
    │  HTTPS (portal's public IP / hostname)
    ▼
┌────────────────────────────┐
│ portal/                    │  - the only component users talk to
│ UI, login, service registry│  - decides WHO may use WHAT
│ admin, audit logs, SQLite  │
└─────────────┬──────────────┘
              │  HTTPS to the gateway's FABNetv4Ext public IP
              │  + shared secret, from the portal's IP only
              ▼
┌────────────────────────────┐
│ gateway/                   │  FABRIC VM with FABNetv4Ext + FABnetv6
│ stateless relay            │  - no database, no user logins
│                            │  - only forwards to FABnetv6 addresses
└─────────────┬──────────────┘
              │  HTTP over FABnetv6 (2602:fcfb::/40)
              │  + the user's FABRIC service token
              ▼
┌────────────────────────────┐
│ service_node/              │  Service author's VMs, in their own slices
│ author's Flask app         │  - checks the user's token with FABRIC
└────────────────────────────┘
```

External services don't use the gateway: the portal just links to them.

| Folder | Runs on | Config file | Deploy |
|---|---|---|---|
| `portal/` | VM with a public IP | `portal/portal.env` | `sudo bash deploy.sh` |
| `gateway/` | FABRIC VM: FABNetv4Ext public IP + FABnetv6 | `gateway/gateway.env` | `sudo bash deploy.sh` |
| `service_node/` | Service authors' slice VMs | env vars (see the example) | `python3 example_app.py` (or the generated `app.py`) |
| `tests/` | Your laptop | — | `python -m pytest tests` |
| `docs/` | — | — | `SETUP.md` (deploy steps), `DESIGN.md` |

## The two config files

Copy each `*.env.example` to `*.env` and replace every `changeme` value
(`deploy.sh` refuses to run while any is left). They share one value, and each
holds the other's address:

| Setting | `portal.env` | `gateway.env` |
|---|---|---|
| Shared secret (must match) | `GATEWAY_SHARED_SECRET` | `GATEWAY_SHARED_SECRET` |
| Where the other side is | `GATEWAY_URL=https://<gateway public IP>` | `GATEWAY_ALLOWED_SOURCES=<portal public IP>/32` |
| Gateway TLS cert | `GATEWAY_TLS_VERIFY=/path/to/gateway.crt` (or `false` for testing) | generated by `deploy.sh` |
| Service node network | `PORTAL_SERVICE_NODE_NETWORK` | `GATEWAY_ALLOWED_TARGETS` |

`sudo FLASK_APP=app.py venv/bin/flask check-gateway` (in `portal/`) checks the
URL, TLS cert, IP allowlist and secret in one call.

## Two kinds of service

The author picks one on the registration form:

| | **App on my FABRIC nodes** (`fabric_token`) | **External web service** (`external`) |
|---|---|---|
| Use when | The service runs on the author's slice VMs | Already a website with its own login |
| Who checks the user | The portal (project membership) **and** the node (checks the token with FABRIC) | The website itself |
| Node receives | `Authorization: Bearer <user's FABRIC service token>` + `X-Fabric-User-Uuid/Name` | — (not proxied) |
| Author registers | allowed projects, FABnetv6 nodes, widget | a URL |
| Author runs | the generated `app.py`, `service_node/example_app.py`, or their own existing API (any path, if it checks the token) | nothing |
| Usable without the portal | Yes: `curl -H "Authorization: Bearer $FABRIC_TOKEN" http://[node]:8080/...` | Yes, it's a website |

Browser cookies and headers never reach the node.

## Login and tokens

However a user logs in, the login code's only job is to obtain their FABRIC
token and call one function. The portal does the rest:

```
any login method ──► login_with_fabric_token(token)
                       ├─ only "service" tokens accepted (see below)
                       ├─ FABRIC user service: who is this? ALL their projects (from their roles)
                       ├─ in PORTAL_PROJECT_ID (portal.env)? → may register services
                       ├─ in a service's allowed projects?   → may use it
                       ├─ token kept server-side             → passed to service nodes
                       └─ session started
```

The project list comes from the user's roles in FABRIC, not from the token's
contents, so any valid token gives the full list.

**Only FABRIC _service_ tokens are accepted.** FABRIC tokens carry a `scope`
claim: `resource` tokens can create and delete slices as the user, `service`
tokens only identify them. Because the portal passes the user's token to
service nodes, it refuses any token whose scope isn't
`PORTAL_REQUIRED_TOKEN_SCOPE` (default `service`). The generated node apps
refuse non-service tokens too, so users calling a node directly from their VMs
also need a service token (not the `resource` token a JupyterHub notebook uses).

The token is kept server-side (`user_tokens` table, deleted at logout).

### Logging in today: the token test page

The login page has a **Sign in with FABRIC** button for the automated login
(e.g. CILogon), which is still to be added: it goes to `PORTAL_LOGIN_URL` and is
disabled until that is set.

Until then, use `https://<portal>/token_test` (linked from the login page as
"For testing"). Paste a FABRIC service token from the FABRIC portal: it shows
the user, **all** their projects (the portal project is marked), whether they
may register services, and which services they can use, without saving
anything. Then click **Log in with this token**.

### Adding the automated login (e.g. CILogon)

One function to call: once the login flow has the user's FABRIC **service**
token, call `login_with_fabric_token(token)` in `portal/routes/auth.py`, then set
`PORTAL_LOGIN_URL` in `portal.env`. It does everything else (scope check,
FABRIC lookup, projects, permissions, storing the token, session). Step-by-step
with example code: [docs/SETUP.md, section 4](docs/SETUP.md#4-adding-the-automated-login-eg-cilogon).

## Running the tests

```bash
cd fabric_service_marketplace
python3 -m venv venv && source venv/bin/activate
pip install -r portal/requirements.txt -r gateway/requirements.txt pytest
python -m pytest tests -v
```

The tests run without FABRIC. They start the real gateway as a separate
process, a stand-in for FABRIC's user service (`tests/fabric_uis_standin.py`,
which issues realistic service and resource tokens), and the portal, then run
node apps on `[::1]`: a header-echo node, the example app, and freshly
generated apps (GET and POST). They cover both kinds of service end to end,
direct calls to nodes with valid, forged and resource tokens, the gateway's
security checks, and upgrading old databases.
